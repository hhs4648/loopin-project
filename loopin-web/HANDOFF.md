# 인수인계 — 학습 교사 웹 (2026-08-12)

출시 준비를 하며 학생 앱·교사 웹·Supabase를 한 번씩 훑었습니다.
**제품 표시 이름은 `학습`이다.** (코드·폴더는 `haksup-*`)
**규칙은 `AGENTS.md`가 단일 소스입니다.** 이 문서는 규칙이 아니라 **배경과 함정**입니다.

> 학생 앱 쪽 함정은 그 리포의 `HANDOFF.md`에 따로 있습니다(폴더가 달라 여기서는 못 읽습니다).

## 0. 마이그레이션 001~013을 전부 올려야 합니다

학생 앱이 **`012`의 DB 트리거에 의존**합니다. 점수·진행률을 앱이 더 이상 올리지 않고
서버가 계산합니다. 빠지면 답안은 저장되는데 집계가 0에서 멈춥니다.

이번에 새로 추가된 것들:

| 번호 | 내용 | 없으면 |
|---|---|---|
| 008 | `enrollments` DELETE 정책 | **학생을 지워도 되살아남** |
| 009 | `class_assignments.open_at` + 학생 조회 제한 | 예약 공개가 안 걸리고 즉시 공개 |
| 010 | `answers` UPDATE 정책 | 같은 문항 재응답이 RLS에 막혀 **조용히 유실** |
| 011 | `error_reports` 표 (넣기 전용) | 학생 앱 오류 신고 실패 |
| 012 | `attempts` 점수 계산 트리거 | **학생 점수·진행률이 0에서 멈춤** |
| 013 | `ensure_rls` 이벤트 트리거 | 새 테이블에 RLS가 자동으로 안 켜짐 (그물이 없어짐) |

### 013은 실제 DB에서 발견해 뒤늦게 편입한 것입니다 (2026-08-22)

`rls_auto_enable()` 함수와 `ensure_rls` 이벤트 트리거는 **파일에 없이 DB에만**
있었습니다. 누군가 SQL Editor에서 직접 만들고 기록을 남기지 않은 것입니다. 스키마를
재생성하려고 실제 스키마를 떠서 대조하다가 발견했고, 안 챙겼으면 조용히 사라질
뻔했습니다.

**교훈: 스키마 변경은 SQL Editor에 저장하지 말고 `supabase/migrations/`에 파일로
남기세요.** SQL Editor로 직접 실행한 것은 `supabase_migrations.schema_migrations`에
기록되지 않아서(그건 CLI `db push` 전용), 나중에 무엇이 올라갔는지 알 방법이 없습니다.
확인이 필요하면 실제 스키마를 떠서 파일과 대조하는 수밖에 없습니다.

`error_reports`는 **읽기 정책이 없습니다.** 일부러 그렇게 뒀습니다 — API로는 아무도
못 읽고, 개발자만 대시보드(service role)로 봅니다. 앱에서 남의 신고를 긁어갈 수 없습니다.

## 1. 과제 예약 공개 — `open_at`

과제를 만들 때 **「수업일 + 그 반의 수업 종료 시각」**을 계산해 절대 시각으로 박아 둡니다
(`src/lib/assignment-open-at.ts`). 학생 앱은 그 시각이 지나야 과제를 봅니다.

- 종료 시각을 찾는 순서: **일회성 수업 → 요일별 시간표 → 통합 시간표**
- 시간표가 비어 있으면 그날 **자정(KST)**
- **한국시간 고정(+09:00)**입니다. Postgres의 `current_date`는 UTC라 그대로 쓰면
  한국 자정보다 9시간 늦게 열립니다
- **오답 재출제는 예외로 즉시 공개**입니다(`sourceAssignmentId`가 있으면 건너뜀).
  교사가 「앱에 내기」를 누른 자리에서 헬스장에 떠야 하는 것이라 수업 종료까지
  미루면 흐름이 끊깁니다

**왜 낼 때 박아 두나:** 나중에 반 시간표를 고쳐도 이미 낸 과제의 공개 시점이 흔들리면
안 되고, 읽는 쪽에서 시간대를 다시 따질 필요도 없습니다.

교사 목록에 아직 안 열린 과제는 **「예약 · N월 N일 HH:MM 공개」** 배지가 붙습니다.
이게 없으면 교사가 「출제 실패」로 읽습니다.

## 2. 오답 재출제 — 성이 아니라 헬스장

학생 앱에서 오답 재출제는 **성에 부여되지 않습니다.** 헬스장 화면에서 풉니다.
밀린 게 여러 개면 **오래된 것부터**입니다.

재출제 과제는 학생 수만큼 만들어집니다(20명이면 20개). `reissueBatchId`로 묶고,
`sourceAssignmentId`로 원본을 가리킵니다. 목록에서 묶음으로 보여주고 한 번에 지웁니다.

### 상태 칩은 점수에서 유도하지 마세요

「보완 필요 / 만점」 판정은 **`latestCorrectCount`·`latestAnsweredCount`**를 씁니다.
예전에는 반올림된 점수(0~100)에서 문항 수를 역산했는데, 그래서 「7/7인데 아직 틀림」
같은 값이 나왔습니다. 실제 개수를 쓰세요.

**원본과 재출제 점수를 비교하지 마세요.** 재출제는 틀린 문항만 푸는 것이라 모수가
다릅니다. 그래서 점수 변화(델타) 표시는 전부 걷어냈습니다.

## 3. 학생 삭제는 서버까지 지워야 합니다

로컬 목록에서만 지우면 잠시 뒤 `fetchClassEnrollments` → `mergeEnrolledStudents`가
서버 값을 다시 합치면서 **되살아납니다.** `removeEnrollmentRemote`를 먼저 부르고,
008 정책이 올라가 있어야 합니다.

**주의:** PostgREST의 `.delete()`는 RLS에 막혀 0행이 지워져도 **에러를 주지 않습니다.**
성공한 것처럼 보이고 다음 동기화에서 되살아납니다. 「지워졌다」를 확인하려면
삭제 후 행이 남아 있는지 따로 봐야 합니다. (지금 코드는 거기까지는 안 합니다.)

## 4. lint 오류 32건 — 그중 일부는 규칙이 틀린 경우입니다

시작은 55건이었고 **동작이 바뀌지 않는 것 23건**을 고쳤습니다.

### 고친 것

- **렌더 중 ref 쓰기 21건.** React는 렌더를 중단하고 다시 시도할 수 있어서, 버려진
  렌더가 남긴 값이 그대로 남습니다.
  - `CalendarEventsOverlay` — 드래그용 「최신 값」 ref들을 effect로 옮김(포인터
    이벤트에서만 읽으므로 커밋 뒤 갱신으로 충분)
  - `NewProblemSetPanel` — ref를 「마운트당 한 번」 캐시로 쓰며 `useState` 초기화 함수
    안에서 채우고 있었는데, 초기화 함수는 원래 한 번만 도는 게 보장되므로 **캐시가
    불필요**했습니다. 통째로 제거
  - `AssignAssignmentModal` — 「방금 리셋했으니 저장 건너뛰기」 플래그를 렌더 중에
    세우던 것을, effect에서 리셋 키만 비교하도록 변경
- `prefer-const` 2건, `ClassSettingsPanel`의 prop→state 동기화 1건

### 남은 32건 — 성격이 갈립니다

**(가) 규칙이 맞는 경우** — 모달 열릴 때 폼 초기화 같은 것. `ClassSettingsPanel`에
적용한 **「렌더 중 조정」**(React 권장) 방식으로 고칠 수 있습니다.

```tsx
const [syncedClass, setSyncedClass] = useState(teacherClass)
if (syncedClass !== teacherClass) {
  setSyncedClass(teacherClass)
  setName(teacherClass.name)
  // …
}
```

> **⚠️ 비교 기준을 좁히지 마세요.** 저는 처음에 `teacherClass.id`로 비교했다가
> 되돌렸습니다. 원래 effect의 의존성은 **객체 자체**였고, `id`로 좁히면 같은 반의
> 값이 밖에서 바뀌었을 때 반영되지 않습니다. **의존성 의미를 그대로 옮기세요.**

**(나) 규칙이 틀린 경우** — 예를 들어:

```tsx
useEffect(() => {
  setOpenGrades(loadOpenGrades())   // localStorage
  setHydrated(true)
}, [])
```

Next.js에서 localStorage는 **마운트 후에 읽어야만** 합니다(서버 렌더와 값이 다르면
하이드레이션이 깨짐). 코드가 맞고 규칙이 이 아키텍처를 모르는 것이라,
**억지로 고치면 오히려 나빠집니다.** 사유를 적은 예외 처리가 맞습니다.

테스트가 없는 UI라 20건을 한 번에 바꾸면 회귀 위험이 실질적입니다.
**한 파일씩, 화면을 확인해가며** 하세요.

## 5. 학생 앱과 조용히 어긋나는 것들

`AGENTS.md`의 대응표를 꼭 보세요. 특히 **문항 id 접미사**(`:match` `:ox` `:ox:fix` …)는
학생 앱이 만들고 여기(`parseAnswerQuestionId`)가 파싱합니다. 한쪽만 고치면 과거 문제집이
조용히 깨집니다.

문제집은 유형을 **라벨 문자열**로 저장합니다. 목록에서 유형을 빼도 과거 문제집에는
그 라벨이 남으니, 학생 앱 빌더는 지우면 안 됩니다.

## 6. 교사 웹은 앱에 안 들어갑니다

학생 앱에서 선생님으로 온보딩하면 **선생님 웹 링크 안내 화면**으로 갑니다
(학생 앱의 `VITE_TEACHER_WEB_URL`). 여기가 **1557×973 데스크톱 고정 레이아웃**이라
폰에서 열면 못 쓰기 때문에, 그 화면은 링크 버튼보다 **주소 복사**를 주 버튼으로 뒀습니다.

교사 로그인은 랜딩페이지에서 처리할 예정입니다(사용자 결정).

> **알아둘 것:** `teacher-session.ts`는 아직 `signInAnonymously()`입니다. 즉
> **브라우저 저장소를 지우면 자기가 만든 반·문제집의 소유권을 잃습니다**
> (`classes.teacher_id = auth.uid()`). 로컬이 원본이라 로컬 데이터도 같이 날아갑니다.
> 랜딩페이지 로그인을 붙일 때 이 익명 세션을 **실제 계정에 이어 붙이는**(link) 경로를
> 같이 만들어야 기존 데이터를 잃지 않습니다.

## 브랜드 변경 — 루핀 → 학습(Haksup) (2026-08-21)

교사 웹이 브라우저에 들고 있는 것(반·학생·문제집·과제 부여·캘린더·로그인 토큰)의
localStorage 키가 전부 `loopin-*` → `haksup-*`로 바뀌었습니다.

**키 이름만 바꾸면 선생님이 만들어 둔 것이 전부 사라진 것처럼 보입니다.**
그래서 `src/lib/legacy-brand-storage.ts`의 스크립트가 구 키를 새 키로 한 번 옮깁니다.

- `layout.tsx`가 **인라인 `<script>`로 주입**합니다. 리액트 effect는 자식이 먼저
  돌고, 저장소를 읽는 모듈이 그보다 먼저 평가될 수 있어 늦습니다.
- `haksup-class-students:{classId}` 처럼 **id가 붙는 키**도 접두사 규칙으로 같이 옮깁니다.
- 이 파일에 남은 `loopin` 문자열은 흔적이 아니라 **옛 키를 찾는 열쇠**입니다.

폴더 이름(`loopin-project` · `loopin-web`)은 그대로입니다(사용자 결정). 문서·주석의
경로 표기를 바꾸지 않은 이유입니다. `package.json`의 `name`만 `haksup-*`로 바꿨습니다.
